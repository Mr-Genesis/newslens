## Vision

### 10x Check
NewsLens stops being a curated 8-story briefing and becomes a **personal intelligence feed you can point at anything**: type "US Iran War" or "Cockroach Janta Party protest" and a living category forms, updates, and badges you when it moves. Every persona field you fill in visibly changes the product. Every story you *see* (not just tap) trains the ranker from user #1, so by the time there are 100 users the recommendation engine has months of signal none of the competitors' cold-start users have.

## Workstreams (each = one PR, TDD)

### WS-1 · Impressions first (PERISHABLE — ship before everything)
**Why first:** every day unlogged is training data lost forever; the graph is retroactively derivable, impressions are not.
- New RLS table `impressions` (id, user_id, cluster_id, article_id NULL, surface TEXT CHECK in briefing|feed|rail|discover|search, created_at). Index (user_id, created_at).
- `POST /impressions` batched: client buffers visible-card ids (IntersectionObserver ≥50% for ≥1s), flushes every 5s or on navigation; server dedupes per (user, cluster, surface, day) via ON CONFLICT DO NOTHING targeting a unique index on (user_id, cluster_id, surface, day) where `day` is a **stored `DATE NOT NULL DEFAULT CURRENT_DATE` column** (an expression index on `date(created_at)` is not IMMUTABLE over timestamptz in Postgres — don't try it).
- Dwell **write path**: the auto-`read` row is created server-side on `GET /clusters/{id}` (routes.py:384-397), keyed to the cluster's REPRESENTATIVE article — there is no way to attach duration today. Spec: `POST /feedback` with `feedback_type="read"` + new `duration_ms` field, sent with **`cluster_id` (server resolves the same representative article** the auto-read used — the client must NOT guess an article id, or it creates a second row); **upserts** the existing row with `duration_ms = GREATEST(existing, new)`. Client fires it on story close/blur.
- Negative signal: **add negative-weight support** to `bump_relevance` (`less` → weight -0.5): clamp `engagement_raw ≥ -1.0` per entity; negative bumps do **NOT** refresh `last_event_at` (refreshing would reset the decay clock on previously accumulated positive signal); add scorer tests with negative AVGs. Note for implementers: the feed blend's `rel = min(1.0, …)` (routes.py:301) is a **ceiling, not a floor** — negatives intentionally flow through and demote; do NOT "fix" it with a 0-floor or WS-1's negative signal is silently neutered.
- Volume guard: max 500 impression rows/user/day (server-side cap, drop + log beyond). Client buffer caps at 200 (drop-oldest, vitest-covered). ONE shared `useImpressions` hook consumed by briefing/feed/rails/discover — never four copies.
- **Indexes (eng review):** the WS-1 migration also adds `ix_articles_published_at (published_at DESC NULLS LAST)` + `ix_articles_fetched_at` — articles has NEITHER today; the feed already sorts unindexed and as_of/rails add more predicates on these columns.
- **CTR numerator (outside voice):** `user_feedback` also gains a nullable `surface` column in THIS migration, and the dwell/read POST carries `surface` — otherwise CTR-per-surface has a denominator (impressions) but no numerator (clicks). Must ride WS-1 or click-attribution is lost the same way impressions were.
- **Clusterless cards (outside voice):** briefing article-fallback cards have no cluster_id, and NULLs never conflict in a unique index (dedupe would silently stop deduping). Dedupe key = (user_id, COALESCE(cluster_id, 0), COALESCE(article_id, 0), surface, day) via expression unique index; impressions accept cluster_id OR article_id (CHECK: at least one non-null).
- Alembic migration (impressions + user_feedback.duration_ms + user_feedback.surface). Deploy note: prod migrates via release alembic; dev DB needs hand-ALTER (create_all-managed).

### WS-2 · Follow Anything (the "+", saved-search rails, home section)
- **Write path (exists):** `POST /follows kind=saved_search` — add per-user cap (20 saved searches, 400 beyond) + trim/normalize value.
- **Evaluation = existing /search machinery, read-time:** `embed_query_cached(phrase)` (in-process memo; cold start re-embeds N phrases in one pass — acceptable) → pgvector HNSW ANN over articles + ILIKE keyword leg + **entity-name exact leg** (alias_norm match). No schema change; no stored embedding column (revisit if follows exceed ~50/user).
- **Precision guard (the "US Iran War ≠ all Middle East" problem):** admit a cluster iff (semantic distance < T_loose AND keyword-or-entity hit) OR distance < T_tight. **T values are MEASURED, not guessed (outside voice):** nobody has ever observed a query→article distance in this system (search discards it, and RETRIEVAL_QUERY vs RETRIEVAL_DOCUMENT embeddings have their own distance distribution — clustering's 0.15 doc↔doc threshold does NOT transfer). Pre-WS-2 gate: a 30-min script logs real distances for ~20 phrases against the prod corpus → pick T_loose/T_tight from the histogram (starting hypotheses 0.35/0.22). Rails logs a distance histogram per eval so drift is visible. Config-gated; fixture tests with adversarial phrases run against REAL recorded distances (CI mocks embeddings — a mocked-embedding threshold test is tautological, so fixtures pin recorded vectors).
- **New endpoint `GET /follows/rails`:** loops ALL the caller's rail-able follows server-side (client makes ONE request) — `saved_search` (hybrid query), `topic` (topic-membership match), **and `entity`** (via `article_entities` — an entity follow gets a rail too; only `source` follows are excluded, since the tier gate already surfaces them in the feed). Recency window 72h (config); groups by cluster; returns per-follow: {follow, stories[≤5], new_count since `follows.last_viewed_at`, total}. Reuses BriefingStory shape so StoryCard renders unchanged. **Latency budget (eng review):** rails evaluate SEQUENTIALLY (no new async patterns) behind a 60-second per-user in-process response cache, invalidated by POST /follows and /follows/{id}/seen (cache-invalidation test required); home renders briefing first, rails hydrate from their own request. /seen taps are optimistic-UI with a retry queue (offline tap must not lose the clear). Rails runs its OWN pgvector query (modeled on /search's) that additionally SELECTs `embedding <=> :v AS dist` (search's discards distance — the precision guard needs it) and puts the recency predicate INSIDE the WHERE (top-k post-filtering can starve recent matches — raise k to ~50 and/or enable hnsw.iterative_scan).
- **Badges (C4) — per-follow, not global:** new column `follows.last_viewed_at` (migration #2 of 3, by PR order) + `POST /follows/{id}/seen`. `new_count` = rail stories newer than it. **Badge clears when** the user taps a story in that rail OR taps the rail header ("see all") — both fire /seen for that follow only. Merely scrolling past does NOT clear. (The global `User.last_seen_at` is unusable here: `GET /digest` resets it on every read — routes.py:1832 — and one timestamp can't express per-follow counts.)
- **Frontend:** "+" on /following becomes a real button → sheet with text input (+ chips of trending topics as suggestions) → addFollow(kind="saved_search"). /following lists each follow with a 3-story preview + unfollow. Home gets "News You Follow" rails (wire diagram): after TOP STORY hero, before category sections; one horizontal rail per follow with the "N new" badge; empty follow shows "nothing new — we're watching" (not hidden — trust the machine visibly).

### WS-3 · Home infinite scroll (stable pagination)
- Home = briefing (top 8, unchanged) + rails (WS-2) + **"All stories" infinite feed** below.
- **Cross-section dedupe (outside voice):** one story must render ONCE on home — precedence hero > rails > category sections > infinite feed; each lower section filters ids already rendered above (client-side Set threaded down). Without this a followed topic's top story appears 3×.
- **Stability fix (required, found in research):** under personalization, `/feed` re-fetches+re-ranks a shifting 500-article pool per request → page N+1 can duplicate/drop vs page N. Add optional `as_of` cursor: server pins the window to `fetched_at <= as_of` (first response returns as_of=now); UER scores may still drift → client ALSO dedupes by article id on append. Pull-to-refresh resets as_of. **`as_of` applies to BOTH paths** — the legacy OFFSET path has the identical top-shift duplicate/drop problem (new ingest shifts offsets), and the fix is the same one WHERE clause.
- Frontend: `useInfiniteFeed` hook — IntersectionObserver sentinel, **prefetch page N+1 as page N renders** (user's requirement), append+dedupe, terminal state at `total`. Reused on /feed screen. No virtualization until >300 DOM cards (measure first).
- Document: personalized `total` caps at 500 by design.

### WS-4 · Back-button behavior + guideline
- **Platform gating (outside voice):** ALL of the below is wrapped in `Capacitor.isNativePlatform()` — one codebase serves web too, and replace-on-tab-nav would make the BROWSER back button exit the site from any tab. Web keeps stock browser semantics (pushes + normal back).
- **Tab-switch history semantics (decided, Material-standard, NATIVE ONLY):** bottom-tab navigations use `router.replace` (tabs never stack history — prevents back walking through every prior tab switch). Hardware back: (a) non-root route (story, settings sub-screens) → `router.back()`; (b) **non-home tab root** (Discover/Saved/Search/Following/Profile) → `router.replace("/")` — one hop to Today, matching "Following→back returns to Today"; (c) **home (Today)** → first press toast "Press back again to exit", second within 2s → `App.minimizeApp()`. Never `exitApp()`.
- Verify the shared `NavBar` back control renders (and calls router.back()) on all NON-root routes; do **not** add "← Back" headers to tab roots — the tab bar is their navigation (adding one would contradict the root model).
- Add to `frontend/CLAUDE.md`: **Back-behavior guideline** — hardware back = previous screen; non-home tab root = hop to Today; **empty history ANYWHERE (home, or a deep-linked/cold-start non-root) = toast + double-press minimize**; ROOTS matter ONLY for the hop/minimize branches (any route with real history just pops); every new route must be classified; tab-bar navs use replace, stacked navs use push.

### WS-5 · Signal-first graph + unified scorer (the honest "G3 for recs")
- **`entity_edges` table** (src_entity_id, dst_entity_id, weight, updated_at; PK (src,dst)): nightly job aggregates co-occurrence (entities sharing a cluster) with exponential decay; idempotent upsert; bounded to top-50 edges per entity.
- **One-hop interest expansion:** candidate entities = edges from the user's high-UER/followed entities, weighted by edge×affinity; a small additive term (config `expansion_weight=0.1`, bounded) into `score_clusters_relevance` — an "adjacent interests" nudge, byte-identical when user has no signal (preserves the G2 no-op invariant).
- **Unified scorer:** extract the feed blend (recency+relevance×cred×specialty) into `services/ranking.py`; feed, rails ordering, and discover deck ordering consume it (one place to tune; A/B-able later).
- CTR observability: /stats gains impressions + CTR per surface (uses WS-1 data).
- GraphRAG-G3 (intent router, CTE retrieval, auto-merge) stays DEFERRED per ROADMAP gates — explicitly out of scope.
- **Outside-voice challenge, user-resolved:** the outside voice argued entity_edges fails the plan's own perishability test (co-occurrence IS retroactively derivable). USER DECISION 2026-07-04: keep WS-5 as planned; the expansion term is an accepted no-op until affinity signal accumulates.

### Journey storyboard (the follow loop)
1. Sees "+" (home rail header or /following) -> curiosity. 2. /follow/new: types anything ->
   feels power ("it takes free text"). 3. Toast + lands on /following with the rail already
   there -> instant payoff (even the "watching" state proves the machine heard). 4. Next morning:
   home shows the panel with "3 new" amber pill -> the reason to return. 5. Taps a story ->
   badge clears (only that rail) -> trust that counts mean something. 5-second visceral: the
   pager panel is visually NEW against the vertical briefing = "my stuff". 5-year reflective:
   rails ordered by user (drag-reorder DEFERRED, creation order for now).
